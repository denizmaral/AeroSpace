# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

MarSpace is a tiling window manager for macOS, built on AeroSpace (MIT). It ships as two binaries: the `MarSpace.app` server, which manages windows, and the `aerospace` CLI client (compatible with AeroSpace's), which talks to it. More docs: `dev-docs/development.md` (setup), `dev-docs/architecture.md`, `dev-docs/socket-protocol.adoc`, the user guide `docs/guide.md`, and the command docs `docs/aerospace-*.adoc` (the source of the CLI help).

## Build, test, lint

Entry point scripts are in the repo root. All of them source `script/setup.sh`, which:
- requires **bash 5** (not macOS's `/bin/bash` 3.2);
- requires **swiftly**, which pins Swift to `.swift-version`;
- rewrites `PATH` to a minimal set of tools in `.deps/bin`.

| Task | Command |
|---|---|
| Debug build (SPM only) → `.debug/` | `./build-debug.sh` |
| Run debug app | `./run-debug.sh` (turns off a running release AeroSpace.app server while the debug one runs) |
| Run CLI against the server | `./run-cli.sh <args>` |
| Full check (what CI runs) | `./test.sh`: debug build with `-warnings-as-errors`, then `swift-test.sh`, `lint.sh`, `generate.sh`, and a check for uncommitted generated files |
| Unit tests only | `./swift-test.sh` |
| Single suite / test | `swift test --filter DwindleTest` or `swift test --filter 'DwindleTest/testParseConfig'` |
| Format / lint | `./format.sh` (swiftformat) and `./lint.sh` (format + swiftlint + periphery dead-code scan). Tools are downloaded into `.deps/` |
| Regenerate generated files | `./generate.sh` |
| Signed release `.app` → `.release/` | `./build-release.sh [--codesign-identity <id>]`. Needs a code-signing cert (default name `aerospace-codesign-certificate`) |

**Without swiftly or bash 5**, plain `swift build --build-tests` and `swift test` from the repo root still work, as long as Xcode's Swift matches `.swift-version`. The generated `xcode/AeroSpace.xcodeproj` pins `TOOLCHAINS` to a swiftly toolchain id. When building the app bundle with `xcodebuild` directly (from `xcode/`, scheme `AeroSpace`):
- pass `TOOLCHAINS=com.apple.dt.toolchain.XcodeDefault`;
- pass `AEROSPACE_CODE_SIGN_IDENTITY=<identity>`;
- for Release, also pass `AEROSPACE_BUILD_INFO_LDFLAGS="-sectcreate __TEXT __aero_build <file>"`. See the `xcodebuild` step in `build-release.sh`.

Release builds use `SWIFT_TREAT_WARNINGS_AS_ERRORS`, so keep debug builds warning-free (`-Xswiftc -warnings-as-errors`).

The app must be granted Accessibility permission to do anything. Until it is, the server blocks in `waitForAccessibilityPermission_nonCancellable` and the CLI reports "server is not responding". Launch the bundle with `open …/AeroSpace.app`; running the Mach-O directly sends the permission request to the parent process instead.

## Generated files: don't edit by hand

`generate.sh` regenerates all of these. `test.sh` fails if they are out of date.
- `Sources/Common/cmdHelpGenerated.swift` and `Sources/Cli/subcommandDescriptionsGenerated.swift` are generated from `docs/aerospace-*.adoc`. A command's usage and help text live in its doc file.
- `xcode/AeroSpace.xcodeproj` is generated by XcodeGen from `xcode/project.yml`. It is only used to wrap the SPM code into an app bundle, and new Swift files under `Sources/` don't require regenerating it.
- Swift and toolchain versions are set at the top of `generate.sh`, which writes `.swift-version` and the header and platforms of `Package.swift`.

## Architecture

### SPM targets (`Package.swift`)
- **`Common`**: shared by the client and server, mostly command-line argument parsing (`Sources/Common/cmdArgs`).
- **`Cli`**: the `aerospace` client.
- **`AppBundle`**: the server. Nearly all logic lives here, as a library.
- **`AeroSpaceApp`**: a tiny executable entry point that Xcode wraps into `AeroSpace.app`.
- **`PrivateApi`**: wraps `_AXUIElementGetWindow`, the only private API used. The project avoids private APIs and never requires disabling SIP.
- **`Macros`**.
- **`AppBundleTests`**.

Swift settings: Swift 6 language mode, `NonisolatedNonsendingByDefault`, and `strictMemorySafety`. Unsafe calls therefore need explicit `unsafe` expressions.

### Client/server
The CLI parses the arguments, reporting parse errors and printing `--help` itself, then sends them over a Unix socket. The server (`AppBundle/server.swift`) parses them again, runs the command, and returns stdout, stderr and the exit code.

### Commands
- `CmdKind` (`Common/cmdArgs/cmdArgsManifest.swift`) lists all commands.
- Each command's arguments are defined and parsed in `Common/cmdArgs/impl/`.
- Server-side implementations live in `AppBundle/command/impl/`, and `AppBundle/command/cmdManifest.swift` maps one to the other.
- Commands run against a `CmdEnv` (target window or workspace, which `--window-id`/`--workspace` can override) and write to a `CmdIo`.

Checklist for a new command (from `dev-docs/architecture.md`):
- docs in `docs/aerospace-<cmd>.adoc` (the CLI help is generated from it);
- decide whether `--window-id`/`--workspace` make sense;
- an `Action` case (`settings/Action.swift`) if it should be pickable in the settings window;
- then run `generate.sh`.

### Sessions and refresh (`AppBundle/layout/refresh.swift`)
Everything runs on `@MainActor`. Use `Task.startUnstructured`, never `Task {}` or `Task.init`; `lint.sh` enforces this.
- **`runLightSession`**: wraps each CLI command and hotkey. It refreshes the model, runs the body, lays out workspaces, syncs focus to macOS, then schedules a heavy refresh.
- **`runHeavyCompleteRefreshSession`**: triggered by accessibility observer events (`GlobalObserver.swift`). It detects new or closed windows, normalizes, and lays out.

Async functions take a `CancellationMode` (`.cancellable` / `.nonCancellable`). The `_nonCancellable` suffix marks functions that must not be cancelled. Use `die`/`check` for invariants.

### Tree model (`AppBundle/tree/`)
- Each `Workspace` owns:
  - a `rootTilingContainer`;
  - a `floatingWindowsContainer`;
  - containers for macOS-minimized, fullscreen, hidden-app and popup windows.
- A `TilingContainer` has an `orientation` (`.h`/`.v`) and a `layout` (`.tiles`/`.accordion`).
- `TreeNode` (`TreeNode.swift`) owns binding and unbinding, per-child `adaptiveWeight` (sizes inside `tiles` containers), and a most-recently-used child stack that drives focus and new-window placement.
- Windows and containers carry a life status (`tombstones.swift`): dead or invisible nodes can stay in the tree, so prefer `inhabitedChildren` over `children` when counting.
- **Normalizations** (`normalizeContainers.swift`, both on by default and controlled by config):
  - flatten containers that have a single child;
  - force nested containers to the opposite orientation of their parent.
- Workspaces are emulated: windows on invisible workspaces are moved into a screen corner. macOS Spaces are deliberately ignored.

### New-window placement (`AppBundle/tree/MacWindow.swift`)
1. `MacWindow.getOrRegister` classifies a window as popup, dialog or tiling (see "Dialogs" in `docs/guide.md`).
2. A tiling window is bound right after the workspace's most recent window.
3. The `on-window-detected` callbacks run (`runOnWindowDetected`).

`relayoutWindow`, `layout tiling` and `move-node-to-workspace` reuse this placement. `new-window-placement = 'dwindle'` (`tree/dwindle.swift`) then splits the most recent window Hyprland-style, after the callbacks run. Deferred splits are applied per workspace in capture order. Windows detected concurrently therefore end up as if detected one by one, unless something else changes the tree in between.

A tiling window that leaves for a macOS native state (fullscreen, minimized, hidden app) records its `TilingSlot` (`tree/TilingSlot.swift`) and returns to it. Only if the slot is gone is it placed as a new window.

### Layout (`AppBundle/layout/`)
`layoutRecursive.swift` turns the tree and weights into rectangles, records `lastAppliedLayoutPhysicalRect`/`VirtualRect` on each node (also used by mouse resize and moves), and applies frames through the accessibility API.

### Settings (`AppBundle/settings/`) and the runtime config (`AppBundle/config/`)
- The user edits typed `Settings` in the settings window (`settings/ui/`); there is no config file. `SettingsStore` keeps them in `~/Library/Application Support/MarSpace` (checksummed binary plist, atomic writes, backup; an unreadable file is never overwritten).
- `Settings.compile()` (`SettingsCompiler.swift`) turns them into the runtime `Config` (`config/Config.swift`), through the command parser. Invalid parts are reported as `SettingsProblem`s and left out; edits are saved and applied even with problems.
- Changing the stored format: bump `Settings.currentSchemaVersion` and add a step to `SettingsMigration`. Decoding is tolerant (missing fields get defaults).
- The TOML parser (`parseConfig.swift`) is only used to take an AeroSpace config over at the first launch (`SettingsImport.swift`) and for the default settings: `docs/config-examples/default-config.toml` is bundled and must parse without errors or warnings (`ConfigTest.testParseDefaultConfig`).
- A new option: a field in `Settings`, the compiler, a control in the settings window, and `docs/guide.md` if users need to know about it.
- Hotkeys (`HotkeyBinding.swift`) use the HotKey library (Carbon `RegisterEventHotKey`). It consumes the key event and can't tell left from right modifiers. Binding modes enable and disable groups of hotkeys.

## Tests

The tests use Swift Testing. Patterns to follow:
- Suites are `@MainActor @Suite(.serializedGlobally)` with `init() { setUpWorkspacesForTests() }`. The tests share global state and run serially.
- `setUpWorkspacesForTests` turns off **both normalizations** and forces horizontal root orientation. Re-enable the normalizations in a test that depends on them, and call `workspace.normalizeContainers()`.
- Build trees with `TestWindow.new(id:parent:)`; `focusWindow()` sets focus and the most-recently-used window.
- Run commands with `await parseCommand("…").cmdOrDie.run(.defaultEnv, .emptyStdin)`.
- Assert tree shape with `root.layoutDescription`, e.g. `.h_tiles([.window(1), .v_tiles([...])])`.
- Test config parsing with `parseConfig("toml")`, checking `.config`, `.errors` and `.strErrors`.

## Contributing conventions

`CONTRIBUTING.md` says to "read the room": patches, commit messages and tests should look like the existing ones in the repo.

Project values (README):
- settings are edited in the settings window, never in a text file;
- practical features over appearance ("ricing" is low priority);
- avoid "dark magic";
- breaking changes only with careful consideration and a helpful message.
